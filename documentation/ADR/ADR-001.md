# Architecture Decision Record

# ADR-001 — Foundation Architecture

---

## Status

**Accepted**

---

## Version

1.0

---

## Purpose

This ADR defines the fundamental architectural principles of the Math Racers platform.

All other ADRs (Backend, AI, Frontend and Infrastructure) inherit the decisions described here.

No implementation should contradict this document.

---

# Goals

The architecture must be:

- simple to understand;
- easy to extend;
- deterministic where gameplay is involved;
- highly testable;
- AI-friendly;
- modular;
- cloud-independent;
- maintainable for many years.

The project is expected to evolve from a mathematics game into a complete educational platform.

Therefore extensibility is considered a first-class requirement rather than an optimisation.

---

# Architectural Principles

The project follows several high-level principles.

## 1. Domain First

Business rules are the most valuable part of the project.

Everything else exists to support them.

The domain model must never depend on:

- React
- FastAPI
- PostgreSQL
- Docker
- OpenAI APIs
- browser APIs
- third-party libraries

Frameworks may change.

Business rules should not.

---

## 2. Clean Architecture

The system follows Clean Architecture.

```
Presentation

↓

Application

↓

Domain

↓

Infrastructure
```

Dependencies always point inward.

Outer layers may know inner layers.

Inner layers never know outer layers.

---

## 3. Domain Driven Design

The codebase is organised around business capabilities instead of technical layers.

Primary domains are:

- Avatar
- Race
- Mathematics
- Statistics
- Progression
- Achievements
- Accounts
- Assets
- AI Generation

Each domain owns:

- entities
- value objects
- business rules
- domain services
- repositories (interfaces only)
- domain events

No domain directly manipulates another domain's persistence.

---

# Bounded Contexts

The application is divided into bounded contexts.

```
Avatar

Race

Mathematics

Progression

Statistics

Achievements

Asset Generation

Authentication
```

Every bounded context owns:

- database model
- API contracts
- business rules

Cross-context communication happens only through explicit interfaces.

---

# Event-Driven Design

The application uses events extensively.

Examples:

```
AvatarCreated

RaceStarted

ProblemSolved

RaceFinished

AchievementUnlocked

FavouriteAvatarChanged
```

Events represent facts that have already happened.

Events are immutable.

Events are named in the past tense.

---

# Synchronous vs Asynchronous Work

Immediate gameplay operations are synchronous.

Examples:

- validating answers;
- updating race state;
- checking achievements.

Long-running work is asynchronous.

Examples:

- image generation;
- thumbnail generation;
- statistics aggregation;
- email delivery;
- backups.

Gameplay must never wait for slow external services.

---

# Separation of Responsibilities

Every subsystem has one clear responsibility.

## Race Engine

Only simulates races.

Never generates mathematics.

Never draws graphics.

Never calls AI.

---

## Mathematics Engine

Only creates mathematical problems.

Never moves runners.

Never updates UI.

---

## Avatar System

Only manages avatars.

Never renders images.

Never communicates directly with image models.

---

## Asset Pipeline

Only generates and validates assets.

Never contains gameplay logic.

---

## Statistics

Only records historical information.

Never influences gameplay.

---

# Deterministic Gameplay

Gameplay must be deterministic.

Given:

- identical race configuration;
- identical random seed;
- identical answers;
- identical timestamps;

the race outcome must always be identical.

This simplifies:

- debugging;
- testing;
- replay;
- balancing.

Randomness is controlled.

Randomness never means unpredictability for developers.

---

# Single Source of Truth

Every piece of data has exactly one owner.

Examples:

Avatar appearance

↓

Avatar domain

Statistics

↓

Statistics domain

Mathematics

↓

Mathematics domain

Duplicated business logic is forbidden.

---

# Composition over Inheritance

Prefer composition.

Avoid deep inheritance trees.

Example:

Instead of

```
FoxRunner

↓

FastFoxRunner

↓

ChampionFoxRunner
```

use

```
Runner

+

Appearance

+

Personality

+

Statistics
```

This keeps behaviour modular.

---

# Explicit State

State transitions must be explicit.

Example:

```
Draft

↓

Generating

↓

Ready

↓

Favourite

↓

Archived
```

Hidden state changes are prohibited.

---

# Immutable Domain Events

Once published, a domain event cannot change.

Instead of modifying an event:

publish another event.

Example:

```
AvatarCreated

↓

AvatarRenamed
```

Never mutate history.

---

# API Independence

The domain must not know whether it is called from:

- REST
- GraphQL
- CLI
- tests
- background jobs

Use cases expose application services.

Transport layers adapt requests.

---

# Storage Independence

Business logic must not depend on PostgreSQL.

Replacing PostgreSQL with another relational database should not require changes to domain logic.

Persistence details belong to Infrastructure.

---

# AI Independence

LLMs are external providers.

Business logic never directly invokes AI.

Instead:

```
Application

↓

AI Service Interface

↓

Provider Adapter

↓

OpenAI
```

Changing AI providers should not affect business rules.

---

# Framework Independence

React.

FastAPI.

Celery.

Redis.

Docker.

These are implementation details.

The architecture should survive replacing any one of them.

---

# Error Handling Philosophy

Errors are categorised.

Business errors

Examples:

- duplicate avatar name;
- invalid race configuration.

Infrastructure errors

Examples:

- database unavailable;
- network timeout.

AI errors

Examples:

- image generation failure.

Unexpected errors

Examples:

- programming bugs.

Each category follows its own handling strategy.

---

# Logging Philosophy

Log meaningful events.

Avoid noisy logging.

Important logs:

- avatar generation;
- race completion;
- API requests;
- failures;
- retries.

Sensitive information is never logged.

---

# Security Principles

Security is built into the architecture.

Requirements:

- least privilege;
- encrypted secrets;
- secure defaults;
- input validation;
- output encoding;
- authenticated APIs.

Security must never rely on the frontend.

---

# Scalability Philosophy

Premature optimisation is avoided.

However the architecture should scale naturally.

Expected future growth:

- additional subjects;
- multiplayer;
- classrooms;
- AI tutors;
- thousands of avatars;
- millions of statistics records.

Scalability comes from modularity rather than complexity.

---

# Testing Philosophy

Testing follows the testing pyramid.

```
Unit Tests

↓

Integration Tests

↓

End-to-End Tests
```

Business rules should primarily be verified by unit tests.

Every bug should ideally produce a regression test.

---

# Code Quality

The project follows strict engineering standards.

Requirements:

- static typing;
- formatting;
- linting;
- automated testing;
- mandatory code review;
- continuous integration.

Code readability has higher priority than cleverness.

---

# Documentation

Documentation is treated as part of the product.

Core documents include:

- GDD
- ADR
- Art Bible
- Prompt Bible
- API Specification
- Database Schema
- Deployment Guide

Documentation evolves together with the implementation.

---

# Non-Goals

The architecture intentionally avoids:

- microservices;
- distributed transactions;
- event sourcing;
- CQRS complexity;
- plugin architectures;
- premature abstraction.

Version 1.0 prioritises simplicity over theoretical scalability.

These decisions may be revisited if product requirements change.

---

# Consequences

## Advantages

- Simple mental model
- High maintainability
- Easy onboarding
- Strong separation of concerns
- Excellent testability
- AI provider independence
- Framework independence
- Predictable gameplay

## Trade-offs

- More interfaces than a tightly coupled design
- Slightly more boilerplate
- Requires discipline to maintain boundaries
- Some cross-domain workflows require explicit orchestration

These trade-offs are accepted because they improve long-term maintainability.

---

# Summary

This ADR establishes the architectural constitution of Math Racers.

Every subsequent ADR must conform to the following principles:

- Domain-first architecture
- Clean Architecture
- Domain-Driven Design
- Event-driven communication
- Deterministic gameplay
- Explicit ownership of business logic
- Framework independence
- AI provider independence
- Long-term maintainability over short-term convenience

This document is the highest-level architectural authority for the project.
