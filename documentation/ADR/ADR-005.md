# Architecture Decision Record

# ADR-005 — Infrastructure Architecture

---

## Status

**Accepted**

---

## Version

1.0

---

## Purpose

This ADR defines the infrastructure architecture for Math Racers.

The infrastructure is responsible for:

- deployment;
- networking;
- storage;
- background processing;
- observability;
- security;
- backups;
- operational reliability.

Infrastructure exists to support the application—not to influence business logic.

All infrastructure components must be replaceable with minimal impact on the application.

---

# Design Goals

The infrastructure must be:

- simple;
- reproducible;
- inexpensive to operate;
- cloud agnostic;
- containerised;
- observable;
- secure by default;
- suitable for a single developer while capable of future scaling.

Version 1.0 is intentionally designed as a modular monolith.

Infrastructure should reflect this simplicity.

---

# Deployment Model

Version 1.0 uses a **single deployable backend application**.

The deployment consists of:

```
Browser

↓

Nginx

↓

FastAPI

↓

Background Worker

↓

PostgreSQL

↓

Object Storage

↓

OpenAI API
```

Every component has a clearly defined responsibility.

---

# Containerisation

Every server-side component runs inside Docker.

Each service has:

- a dedicated Dockerfile;
- immutable images;
- pinned base images;
- health checks;
- reproducible builds.

Containers must never rely on mutable runtime state.

---

# Docker Compose

Docker Compose is the canonical development and small-production orchestration tool.

Compose manages:

- backend;
- worker;
- PostgreSQL;
- Redis;
- Nginx.

Running the application locally should require only:

```bash
docker compose up
```

No manual dependency installation should be necessary.

---

# Reverse Proxy

Nginx acts as the public entry point.

Responsibilities:

- HTTPS termination;
- static asset delivery;
- request compression;
- caching headers;
- reverse proxy;
- security headers.

Nginx should contain no business logic.

---

# HTTPS

All production traffic must use HTTPS.

Requirements:

- TLS 1.2+
- HTTP → HTTPS redirect
- automatic certificate renewal
- HSTS enabled

Plain HTTP is permitted only for local development.

---

# Static Assets

Static assets are served directly by Nginx.

Examples:

- JavaScript bundles;
- CSS;
- fonts;
- icons.

Generated assets are served from object storage or CDN in future versions.

The backend should not stream static files.

---

# Database

Version 1.0 standardises on PostgreSQL.

Responsibilities:

- relational data;
- metadata;
- statistics;
- progression;
- accounts.

Binary assets are intentionally excluded.

Database access occurs only through the backend.

---

# Object Storage

Generated assets are stored separately.

Examples:

- avatars;
- thumbnails;
- future illustrations;
- exports.

Object storage should provide:

- versioning;
- lifecycle policies;
- durable storage.

The implementation should remain provider-independent.

---

# Redis

Redis is introduced as an infrastructure service.

Responsibilities:

- background job queue;
- distributed locking (if required);
- temporary caching.

Redis must never become the primary data store.

Loss of Redis data must not corrupt application state.

---

# Background Workers

Background workers execute asynchronous tasks.

Examples:

- avatar generation;
- image validation;
- thumbnail creation;
- cleanup;
- scheduled maintenance.

Workers communicate through the job queue.

Workers remain stateless.

---

# Scheduled Jobs

Recurring maintenance tasks include:

- backup verification;
- cleanup of temporary files;
- expired session removal;
- metrics aggregation.

Scheduling should be centralised.

Business logic should never depend on cron timing.

---

# Configuration

Configuration is external.

Sources:

- environment variables;
- configuration files (non-secret);
- secret management.

Examples:

- API keys;
- database URLs;
- object storage credentials;
- feature flags.

Configuration must never be committed to source control.

---

# Secrets Management

Secrets include:

- OpenAI keys;
- database passwords;
- JWT signing keys;
- storage credentials.

Requirements:

- environment injection;
- rotation capability;
- least privilege;
- no logging.

Secrets should never appear in application output.

---

# Logging

Logging is structured.

Every log entry should include:

- timestamp;
- level;
- service;
- correlation ID;
- message.

Preferred levels:

- DEBUG
- INFO
- WARNING
- ERROR
- CRITICAL

Logs should be machine-readable.

---

# Metrics

The system should expose operational metrics.

Examples:

Application:

- request count;
- latency;
- error rate.

AI:

- generation duration;
- retries;
- failures.

Infrastructure:

- CPU;
- memory;
- disk usage;
- queue size.

Metrics should support future monitoring platforms.

---

# Health Checks

Each service exposes health endpoints.

Minimum checks:

Backend

- running;
- database connectivity.

Worker

- queue connectivity.

Database

- accepting connections.

Health checks should be lightweight.

---

# Monitoring

Infrastructure should detect:

- unavailable services;
- excessive response times;
- queue backlog;
- storage failures;
- repeated AI failures.

Monitoring should focus on user impact.

---

# Backup Strategy

Backups include:

Database

- daily full backups;
- transaction log retention where applicable.

Object Storage

- versioning;
- lifecycle protection.

Configuration

- infrastructure repository.

Backups must be tested regularly.

An untested backup is considered unreliable.

---

# Disaster Recovery

Recovery priorities:

1. Database
2. Generated assets
3. Configuration
4. Logs

Recovery procedures should be documented and reproducible.

---

# CI/CD

Every change passes through an automated pipeline.

Typical flow:

```
Commit

↓

Lint

↓

Static Analysis

↓

Unit Tests

↓

Integration Tests

↓

Build Images

↓

Security Scan

↓

Deploy
```

Deployment should require no manual server changes.

---

# Image Versioning

Docker images use immutable version tags.

Avoid mutable tags such as:

```
latest
```

Preferred:

```
1.0.3

2027.04.12

git-sha
```

Deployments should always be reproducible.

---

# Database Migrations

Schema changes are managed through migrations.

Requirements:

- version controlled;
- reversible where practical;
- automated during deployment.

Manual schema modifications are prohibited.

---

# Networking

Only Nginx is publicly accessible.

Internal services communicate through a private network.

Direct public access to:

- PostgreSQL;
- Redis;
- workers

is prohibited.

---

# Scalability

The infrastructure should scale incrementally.

Future scaling options:

- multiple backend instances;
- dedicated worker pools;
- CDN for assets;
- managed PostgreSQL;
- managed object storage.

Scaling should not require architectural redesign.

---

# Security

Infrastructure security requirements:

- least privilege;
- firewall restrictions;
- automatic security updates;
- dependency scanning;
- container isolation;
- non-root containers;
- read-only filesystems where practical.

Security should be enabled by default.

---

# Dependency Management

Application dependencies are pinned.

Container base images are versioned.

Regular dependency updates should be automated and reviewed.

---

# Observability

Every request should be traceable across:

```
Browser

↓

Nginx

↓

Backend

↓

Worker

↓

Database

↓

AI Provider
```

Correlation IDs should propagate through the complete request lifecycle.

---

# Local Development

Local development should closely resemble production.

Developers should be able to:

- start the stack with Docker Compose;
- run automated tests;
- inspect logs;
- connect to PostgreSQL;
- execute background workers.

Environment differences should be minimal.

---

# Cloud Independence

The application should avoid vendor lock-in.

Infrastructure interfaces should support:

- AWS;
- Azure;
- Google Cloud;
- Hetzner;
- self-hosted environments.

Cloud-specific features should remain optional.

---

# Future Evolution

Future infrastructure enhancements may include:

- Kubernetes;
- CDN integration;
- autoscaling;
- distributed workers;
- multi-region deployment;
- managed observability;
- blue/green deployments.

Version 1.0 should not introduce this complexity prematurely.

---

# Non-Goals

Version 1.0 intentionally excludes:

- Kubernetes;
- service mesh;
- microservices;
- distributed databases;
- event streaming platforms;
- multi-region deployment;
- complex orchestration frameworks.

Operational simplicity is preferred over maximum scalability.

---

# Consequences

## Advantages

- Low operational complexity.
- Fast local development.
- Reproducible deployments.
- Clear separation of infrastructure concerns.
- Cloud independence.
- Easy maintenance by a single developer.
- Straightforward future scaling.
- Reliable disaster recovery strategy.

## Trade-offs

- A modular monolith limits independent service deployment.
- Docker Compose is less flexible than Kubernetes at large scale.
- Single-region deployment reduces geographic redundancy.
- Some future scaling features will require infrastructure evolution.

These trade-offs are accepted because they optimise for rapid development, maintainability and operational simplicity.

---

# Summary

The Math Racers infrastructure is intentionally designed as a **simple, cloud-agnostic, containerised platform** centred around a modular monolith.

It prioritises reproducibility, maintainability and developer productivity while providing clear paths for future growth. Infrastructure complexity is introduced only when justified by real product requirements, ensuring that operational overhead remains proportional to the needs of Version 1.0.
