# Architecture Decision Record

# ADR-003 — AI Architecture

---

## Status

**Accepted**

---

## Version

1.0

---

## Purpose

This ADR defines the complete AI architecture for Math Racers.

AI is responsible for **creating content**, never for **executing gameplay**.

This separation guarantees that:

- races remain deterministic;
- gameplay works offline;
- AI providers can be replaced;
- generated content remains reproducible.

AI is a creative subsystem—not a gameplay subsystem.

---

# Design Philosophy

The AI architecture follows one fundamental principle:

> **AI generates assets. The game consumes assets.**

The game should never depend on an LLM response during gameplay.

Every AI request produces reusable content that becomes part of the player's collection.

---

# AI Responsibilities

The AI subsystem owns:

- avatar descriptions;
- avatar names;
- avatar biographies;
- image prompt generation;
- character illustrations;
- future story content;
- future educational hints.

The AI subsystem does **not** own:

- mathematics;
- race simulation;
- statistics;
- achievements;
- progression logic;
- balancing.

---

# AI Architecture

```
Frontend

↓

Backend API

↓

Application Service

↓

AI Orchestrator

↓

Prompt Builder

↓

Provider Adapter

↓

OpenAI API

↓

Validator

↓

Asset Storage

↓

Database
```

Every stage has a single responsibility.

---

# AI Pipeline

Every generation request follows the same pipeline.

```
Validate Input

↓

Build Metadata

↓

Generate Structured Content

↓

Generate Prompt

↓

Generate Asset

↓

Validate Result

↓

Persist

↓

Notify Client
```

The pipeline must be deterministic except for the final creative generation.

---

# AI Orchestrator

The AI Orchestrator coordinates every generation workflow.

Responsibilities:

- workflow sequencing;
- retry policy;
- provider selection;
- validation;
- persistence coordination;
- error recovery.

The orchestrator never generates prompts directly.

---

# Prompt Builder

Prompt construction is a dedicated subsystem.

Responsibilities:

- convert metadata into prompts;
- inject style guides;
- inject quality constraints;
- inject technical requirements.

Prompt generation must be deterministic.

Identical metadata must always produce identical prompts.

---

# Structured Metadata

Every generation begins with structured metadata.

Example:

```yaml
species: fox

fur_color: orange

hair: short

eyes: green

accessory: blue headband

style: sporty

emotion: happy
```

This metadata becomes the source of truth.

Images are derived from metadata—not the reverse.

---

# Prompt Versioning

Every prompt has its own version.

Metadata includes:

- prompt version;
- provider;
- model;
- generation date;
- pipeline version;
- asset version.

Prompt changes never invalidate existing assets.

---

# Provider Abstraction

The application never calls an AI provider directly.

Instead:

```
AI Service

↓

Provider Interface

↓

OpenAI Adapter
```

Future providers can be added without changing business logic.

Examples:

- OpenAI
- Azure OpenAI
- Local models
- Future providers

Only adapters change.

---

# Provider Independence

The rest of the application should not know:

- endpoint URLs;
- authentication;
- model names;
- request formats.

These belong exclusively to provider adapters.

---

# Image Generation

Version 1.0 standardises on:

**OpenAI GPT Image**

Responsibilities:

- generate avatar illustrations;
- transparent backgrounds;
- premium quality;
- consistent artistic style.

The image model never invents gameplay mechanics.

---

# Image Requirements

Generated images must satisfy:

- transparent background;
- square aspect ratio;
- full body visible;
- single character;
- child-friendly;
- no text;
- no watermark;
- premium illustration quality.

The Prompt Bible defines artistic details.

---

# Text Generation

LLMs generate:

- names;
- biographies;
- structured descriptions;
- future narrative content.

All generated text must be:

- positive;
- encouraging;
- age appropriate;
- concise.

---

# Deterministic Prompt Construction

Prompt Builder output depends only on:

- metadata;
- prompt version;
- style configuration.

No randomness is introduced.

Randomness belongs exclusively to the image model.

---

# Asset Validation

Every generated asset is validated automatically.

Validation includes:

## Technical

- file exists;
- correct dimensions;
- transparency;
- readable format.

## Content

- exactly one character;
- no inappropriate content;
- no text;
- no cropped body;
- acceptable composition.

Invalid assets are rejected.

---

# Retry Strategy

Failures follow a controlled retry process.

```
Attempt 1

↓

Retry

↓

Alternative Prompt

↓

Retry

↓

Provider Error

↓

Fail Gracefully
```

Retries must be limited.

Infinite retries are forbidden.

---

# Regeneration

Players may regenerate avatars.

Each regeneration creates a new immutable version.

Example:

```
Version 1

↓

Version 2

↓

Version 3
```

Older versions remain available until explicitly removed.

---

# Asset Identity

Every generated asset has immutable metadata.

```
Asset ID

Prompt Version

Pipeline Version

Generation Timestamp

Provider

Model

Status
```

Assets are never modified in place.

---

# Storage

Binary assets are stored in object storage.

Metadata is stored in PostgreSQL.

This separation allows:

- efficient delivery;
- independent scaling;
- version management.

---

# AI Job Processing

Generation is asynchronous.

Workflow:

```
Create Avatar

↓

Queue Job

↓

Worker Executes

↓

Store Result

↓

Update Status
```

HTTP requests should return immediately.

---

# Job States

Every AI job has explicit states.

```
Pending

↓

Running

↓

Succeeded
```

or

```
Pending

↓

Running

↓

Failed

↓

Retrying
```

State transitions are immutable.

---

# Failure Handling

Failures should never interrupt gameplay.

If generation fails:

- preserve metadata;
- preserve request;
- allow retry;
- notify the player politely.

Technical details remain hidden.

---

# Rate Limiting

The AI subsystem should protect provider quotas.

Possible controls:

- per-user generation limits;
- concurrent generation limits;
- worker concurrency limits;
- queue throttling.

Rate limiting belongs to the backend—not the frontend.

---

# Cost Optimisation

AI generation is significantly more expensive than gameplay.

Therefore:

- generate once;
- cache forever;
- reuse assets;
- regenerate only on request.

Gameplay itself should incur zero AI cost.

---

# Prompt Library

Prompts are stored centrally.

Categories include:

- avatars;
- biographies;
- names;
- badges;
- loading artwork;
- future environments.

Prompts are treated as versioned source code.

---

# Prompt Testing

Prompt quality should be measurable.

Useful metrics include:

- acceptance rate;
- regeneration frequency;
- validation failures;
- average generation time;
- user satisfaction.

Prompt engineering is an engineering discipline.

---

# AI Configuration

Configuration includes:

- provider;
- model;
- timeout;
- retry count;
- queue settings;
- prompt version;
- feature flags.

No provider-specific constants should appear in business logic.

---

# Security

AI requests must never expose:

- API keys;
- internal prompts;
- infrastructure details;
- database identifiers.

Secrets remain server-side.

The frontend never communicates directly with AI providers.

---

# Privacy

Only generation data required for creating assets should be sent to AI providers.

Never include:

- authentication tokens;
- email addresses;
- internal identifiers;
- statistics;
- personal progress.

Generated requests should contain only creative metadata.

---

# Observability

Every generation request should record:

- job ID;
- provider;
- model;
- latency;
- retries;
- validation result;
- final status.

This enables reliable monitoring and troubleshooting.

---

# Future Expansion

The architecture should support future AI capabilities without redesign.

Examples:

- animated avatars;
- voice generation;
- interactive stories;
- educational coaching;
- personalised hints;
- comic generation.

Each capability should become another pipeline using the same architectural principles.

---

# Non-Goals

Version 1.0 intentionally excludes:

- AI-generated mathematics;
- AI-controlled race simulation;
- conversational NPCs;
- real-time LLM interaction during races;
- autonomous gameplay decisions.

Educational gameplay must remain deterministic and fully testable.

---

# Consequences

## Advantages

- Complete separation between gameplay and AI.
- Provider independence.
- Deterministic prompt generation.
- Reproducible assets.
- Easy future expansion.
- Low gameplay latency.
- Offline gameplay remains possible.
- Centralised prompt management.

## Trade-offs

- More orchestration code.
- Additional asynchronous workflow complexity.
- Versioned assets require extra storage.
- Validation pipeline increases implementation effort.

These trade-offs are accepted because they produce a reliable, maintainable and scalable AI system.

---

# Summary

The AI subsystem is a specialised content-generation platform.

Its responsibility is to transform structured metadata into high-quality reusable assets while remaining isolated from gameplay.

By separating creative generation from deterministic game logic, Math Racers achieves reproducibility, maintainability and long-term flexibility without sacrificing player experience.
