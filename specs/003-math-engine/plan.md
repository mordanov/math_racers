# Implementation Plan: Mathematics Engine

**Branch**: `003-math-engine` | **Date**: 2026-08-09 | **Spec**: [spec.md](spec.md)

---

## Summary

Implement the Mathematics Engine: a deterministic, seed-based problem generator running entirely in the browser (TypeScript), plus a backend reference generator and difficulty management API (Python/FastAPI). The engine produces tier-appropriate arithmetic problems, validates answers client-side, manages adaptive tier selection, and exposes a reference HTTP endpoint for seed verification and parent override management.

---

## Technical Context

**Language/Version**: TypeScript (frontend engine); Python 3.12/3.13 (backend reference API)  
**Primary Dependencies**: React, Vitest (frontend — all existing); FastAPI, Pydantic v2, SQLAlchemy asyncio (backend — all existing); new: none  
**Storage**: PostgreSQL — one new table: `player_difficulty` (tier + parent override per player). Frontend engine: in-memory only.  
**Testing**: Vitest (frontend unit tests); pytest + pytest-asyncio (backend unit + integration)  
**Target Platform**: Modern browsers (Chrome, Edge, Firefox, Safari current stable); Linux container for backend (python:3.12-slim)  
**Project Type**: Web application — modular monolith (ADR-002); browser-side game engine (ADR-004)  
**Performance Goals**: Problem generation < 1 ms; answer validation < 1 ms (from technical-requirements.md)  
**Constraints**: No network call during gameplay; no external RNG library (Mulberry32 inline); immutable `ProblemSet` instances  
**Scale/Scope**: Per-session in-memory computation; no concurrency target for the engine itself (browser isolation)

## Implementation Notes

### RNG Parity

Both frontend (TypeScript) and backend (Python) must implement Mulberry32 with identical arithmetic. The critical detail: Python integers are arbitrary-precision; the 32-bit mask `& 0xFFFFFFFF` must be applied after every operation to match JavaScript's 32-bit unsigned integer behaviour. This is verified by the parity integration test in `test_problems.py`.

### Tier 6 Fallback

`TIER_CONFIGS` maps Tier 6 to `null` by default. `generateProblemSet` checks: if `tier === 6` and no custom config has been injected, it uses the Tier 5 config. The custom config injection point is a single function parameter (`customTierConfig?: TierConfig`) to keep the fallback logic explicit and testable.

### `player_difficulty` Table

One row per player. Columns: `player_id` (FK → accounts), `current_tier` (integer, default 1), `parent_override` (nullable integer), `updated_at`. The `GET /api/v1/players/{id}/difficulty` endpoint derives `effective_tier` at read time: `parent_override ?? current_tier`.

### Skill Score Update

`selectTier` on the frontend reads the current tier from race session state (passed in via `TierSelectionInput`). It does not write to the backend directly — the statistics/progression system is responsible for persisting the updated tier after race completion. This engine only computes the new tier value.
