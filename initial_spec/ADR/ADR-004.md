# Architecture Decision Record

# ADR-004 — Frontend Architecture

---

## Status

**Accepted**

---

## Version

1.0

---

## Purpose

This ADR defines the frontend architecture of Math Racers.

The frontend is responsible for:

- user interaction;
- gameplay execution;
- race rendering;
- animations;
- mathematical challenges;
- local game state;
- responsive UI.

The frontend is **not** responsible for:

- persistent storage;
- authentication logic;
- AI generation;
- business orchestration;
- long-term statistics.

The browser is the game console.

The backend is the platform.

---

# Design Goals

The frontend must be:

- responsive;
- deterministic;
- highly interactive;
- component-driven;
- offline-capable;
- accessible;
- testable;
- maintainable.

Player interaction should never feel delayed by network communication.

---

# Technology Stack

## Framework

React

Reasons:

- mature ecosystem;
- component architecture;
- excellent tooling;
- large community;
- long-term stability.

---

## Language

TypeScript

TypeScript is mandatory.

No production JavaScript files are permitted.

Reasons:

- type safety;
- better refactoring;
- improved IDE support;
- fewer runtime bugs.

---

## Build Tool

Vite

Reasons:

- extremely fast development;
- excellent TypeScript support;
- simple configuration;
- modern build pipeline.

---

# Frontend Responsibilities

The frontend owns:

- menus;
- race rendering;
- race simulation;
- mathematical exercises;
- animations;
- audio playback;
- local settings;
- accessibility features.

The frontend does **not** own:

- AI generation;
- authentication decisions;
- permanent statistics;
- asset persistence.

---

# Architectural Layers

```
Pages

↓

Features

↓

Components

↓

Shared UI

↓

Infrastructure
```

Each layer has a single responsibility.

---

## Pages

Pages represent complete screens.

Examples:

- Home
- Avatar Gallery
- Avatar Creator
- Race Setup
- Race
- Championship
- Statistics
- Settings

Pages contain layout only.

Business logic belongs to Features.

---

## Features

A feature implements one business capability.

Examples:

```
Avatar Selection

Race Setup

Race Engine

Statistics

Achievements

Settings
```

Each feature is isolated.

Features communicate through explicit interfaces.

---

## Components

Components are reusable UI building blocks.

Examples:

```
Button

Card

AvatarCard

ProgressBar

MathProblem

RaceLane

Dialog

Tooltip
```

Components should remain presentation-focused.

---

## Shared UI

Shared UI contains:

- design tokens;
- typography;
- spacing;
- colours;
- icons;
- animations.

Business logic is forbidden.

---

# Component Philosophy

Components should be:

- reusable;
- composable;
- predictable;
- stateless whenever practical.

Avoid inheritance.

Prefer composition.

---

# State Management

State is divided into three categories.

## Local State

Examples:

- dialog visibility;
- form values;
- hover state.

Lives inside components.

---

## Feature State

Examples:

- current race;
- selected avatars;
- race settings.

Lives inside feature modules.

---

## Server State

Examples:

- avatars;
- statistics;
- achievements;
- user profile.

Retrieved from the backend.

Cached independently.

---

# Race Simulation

The browser owns the complete race simulation.

Responsibilities:

- runner movement;
- timing;
- obstacle progression;
- mathematics;
- animations;
- audio timing.

The backend receives only the completed race result.

This eliminates gameplay latency.

---

# Mathematics Engine

The mathematics engine executes entirely in the browser.

Responsibilities:

- generate problems;
- validate answers;
- measure response times;
- calculate obstacle outcomes.

Benefits:

- instant feedback;
- offline support;
- deterministic behaviour;
- reduced server load.

---

# Rendering

Rendering should remain independent from gameplay logic.

Example:

```
Race Engine

↓

Race State

↓

Renderer

↓

Canvas / DOM
```

The renderer consumes state.

It never modifies gameplay.

---

# Animation Architecture

Animations are driven by state transitions.

Example:

```
Runner Moves

↓

Position Changes

↓

Animation Updates
```

Animation never determines game logic.

Game logic determines animation.

---

# Timing

The game uses a single authoritative game clock.

Animations, timers and race progression reference this clock.

Avoid multiple independent timers.

This guarantees synchronisation.

---

# UI Updates

UI should react to state changes.

Avoid imperative DOM manipulation.

Rendering should be declarative.

---

# API Communication

Frontend communicates exclusively through REST APIs.

No direct database access.

No direct AI provider communication.

Every server interaction goes through the backend.

---

# Error Handling

Frontend errors fall into categories.

## Validation

Display inline.

---

## Network

Allow retry.

---

## AI Generation

Show progress.

Allow regeneration.

---

## Unexpected

Display friendly error screen.

Offer recovery.

Never expose stack traces.

---

# Loading Strategy

Loading should be progressive.

Priority:

1. UI shell
2. Current page
3. Visible assets
4. Background assets

Large images should be lazy-loaded.

---

# Asset Management

Assets are divided into:

Static assets

- icons;
- fonts;
- logos.

Generated assets

- avatars;
- future illustrations.

Generated assets should be cached aggressively.

---

# Offline Support

Offline mode supports:

- races;
- training;
- local settings;
- previously downloaded avatars.

Unavailable offline:

- avatar creation;
- synchronisation;
- cloud statistics.

The UI should clearly indicate offline status.

---

# Accessibility

Accessibility is mandatory.

Requirements:

- keyboard navigation;
- screen reader compatibility;
- sufficient colour contrast;
- scalable typography;
- reduced motion support;
- visible focus indicators.

No gameplay feature should rely exclusively on colour.

---

# Responsive Design

Primary targets:

- desktop;
- laptop;
- tablet.

Secondary target:

- large mobile phones.

The interface should adapt rather than scale.

---

# Design System

A single design system is used across the application.

Defines:

- colours;
- spacing;
- typography;
- shadows;
- radii;
- icons;
- animation durations.

All components consume design tokens.

Hardcoded visual values are discouraged.

---

# Theme Support

Version 1.0 includes one theme.

Future versions may introduce:

- dark mode;
- seasonal themes;
- accessibility themes.

The architecture should support theme switching without component changes.

---

# Audio Integration

Audio playback is event-driven.

Example:

```
Correct Answer

↓

Event

↓

Play Sound
```

Gameplay never waits for audio completion.

---

# Performance

Performance targets:

Initial load:

< 3 seconds

Race start:

< 2 seconds

UI interactions:

< 100 milliseconds

Frame rate:

60 FPS target

30 FPS minimum

Performance should degrade gracefully.

---

# Security

Frontend security includes:

- input sanitisation;
- secure token storage;
- HTTPS only;
- content security policy compliance;
- protection against XSS.

The frontend must assume that all client-side code can be inspected.

Sensitive logic belongs on the backend.

---

# Telemetry

Anonymous telemetry may record:

- crashes;
- performance;
- loading times;
- rendering issues.

Gameplay analytics should remain privacy-conscious.

No educational data should be transmitted unnecessarily.

---

# Future Expansion

The architecture should support:

- Story Mode;
- multiplayer spectators;
- additional educational subjects;
- animated avatars;
- seasonal UI themes;
- classroom mode.

These additions should fit into existing feature boundaries.

---

# Non-Goals

Version 1.0 intentionally excludes:

- server-side rendering;
- micro-frontends;
- multiple frontend frameworks;
- browser-specific implementations;
- runtime plugin systems.

Simplicity is preferred over architectural novelty.

---

# Consequences

## Advantages

- Responsive gameplay.
- Offline race capability.
- Clear separation between rendering and logic.
- Excellent component reuse.
- Strong type safety.
- High maintainability.
- Easy feature expansion.
- Predictable application state.

## Trade-offs

- Larger frontend responsibility.
- More sophisticated client architecture.
- Local race simulation requires disciplined testing.
- Browser performance becomes more important.

These trade-offs are accepted because they maximise responsiveness and minimise operational complexity.

---

# Summary

The frontend is responsible for delivering the complete gameplay experience while remaining independent from backend implementation details.

It executes races locally, renders the game world, manages interaction and provides immediate educational feedback, while delegating persistence, authentication and AI orchestration to the backend.

This architecture creates a fast, reliable and highly maintainable browser-based game.
