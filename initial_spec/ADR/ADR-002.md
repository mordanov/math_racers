# Architecture Decision Record

# ADR-002 — Backend Architecture

---

## Status

**Accepted**

---

## Version

1.0

---

## Purpose

This ADR defines the backend architecture for Math Racers.

The backend is responsible for:

- business orchestration;
- persistence;
- authentication;
- AI orchestration;
- asset management;
- statistics;
- configuration.

The backend is **not** responsible for:

- race rendering;
- animations;
- UI state;
- gameplay simulation.

Race simulation remains in the browser.

---

# Design Goals

The backend must be:

- simple;
- modular;
- stateless;
- highly testable;
- asynchronous where appropriate;
- horizontally scalable;
- easy to deploy.

The expected workload consists of many lightweight requests with occasional long-running AI generation tasks.

---

# Technology Stack

## Language

Python 3.13

Reasons:

- excellent ecosystem;
- modern typing;
- outstanding AI tooling;
- asynchronous support;
- readability;
- long-term maintainability.

---

## Framework

FastAPI

Reasons:

- async-first;
- automatic OpenAPI generation;
- Pydantic integration;
- excellent performance;
- mature ecosystem.

The application should expose a REST API only.

GraphQL is intentionally excluded from Version 1.0.

---

## Runtime

Uvicorn

Multiple workers may be used behind a reverse proxy.

The application itself remains stateless.

---

# Backend Responsibilities

The backend owns the following business capabilities.

```
Authentication

↓

Avatar Management

↓

AI Generation

↓

Asset Storage

↓

Statistics

↓

Achievements

↓

Progression

↓

Administration
```

Gameplay execution is intentionally excluded.

---

# Architectural Layers

The backend follows the structure defined in ADR-001.

```
Presentation

↓

Application

↓

Domain

↓

Infrastructure
```

Each layer has strict responsibilities.

---

## Presentation Layer

Responsible for:

- HTTP endpoints;
- request validation;
- response serialization;
- authentication middleware;
- API versioning.

Must not contain business logic.

---

## Application Layer

Coordinates use cases.

Examples:

```
Create Avatar

↓

Generate Avatar

↓

Store Metadata

↓

Queue Image Generation

↓

Return Job ID
```

Application services orchestrate domains.

They do not implement business rules.

---

## Domain Layer

Contains:

- entities;
- value objects;
- domain services;
- business rules;
- repository interfaces;
- domain events.

The Domain layer must have **zero** dependencies on FastAPI, SQLAlchemy or external APIs.

---

## Infrastructure Layer

Responsible for:

- PostgreSQL;
- object storage;
- OpenAI integration;
- background workers;
- logging;
- configuration;
- external APIs.

Infrastructure implements interfaces defined by the Domain.

---

# Domain Modules

The backend is organised by business capability.

```
accounts/

avatars/

races/

mathematics/

statistics/

progression/

achievements/

assets/

ai/

shared/
```

Each module is self-contained.

Shared code should remain minimal.

---

# Shared Module

The shared module contains only cross-cutting concerns.

Examples:

- Result types;
- identifiers;
- time abstraction;
- event interfaces;
- common exceptions.

Business logic must not migrate into `shared`.

---

# API Design

REST endpoints use nouns.

Examples:

```
GET /avatars

POST /avatars

GET /avatars/{id}

PATCH /avatars/{id}

DELETE /avatars/{id}
```

Nested resources are used only when ownership is explicit.

Example:

```
GET /avatars/{id}/statistics
```

Deep endpoint hierarchies should be avoided.

---

# API Versioning

Every endpoint belongs to an API version.

Example:

```
/api/v1/
```

Breaking changes require a new version.

Minor additions do not.

---

# Request Validation

All requests are validated at the API boundary.

Validation includes:

- required fields;
- formats;
- ranges;
- lengths;
- enums.

Invalid requests never reach domain logic.

---

# Response Design

Responses should be predictable.

Successful operations return structured objects.

Errors return structured error models.

Avoid returning primitive values directly.

Example:

Good:

```json
{
  "id": "...",
  "status": "ready"
}
```

Avoid:

```json
true
```

---

# Business Transactions

One use case corresponds to one transaction whenever practical.

Example:

```
Create Avatar

↓

Persist Metadata

↓

Commit

↓

Queue Image Generation
```

External API calls should never be part of a database transaction.

---

# Repository Pattern

Repositories abstract persistence.

The Domain depends only on interfaces.

Example responsibilities:

AvatarRepository

- save
- load
- delete
- exists

Implementation belongs to Infrastructure.

Repositories should model aggregates, not tables.

---

# Unit of Work

Application services own transactional boundaries.

Repositories should not commit independently.

This guarantees consistency across related operations.

---

# Background Jobs

Long-running work is executed asynchronously.

Examples:

- image generation;
- thumbnail generation;
- statistics aggregation;
- cleanup tasks;
- scheduled maintenance.

HTTP requests should complete quickly.

---

# Job Queue

Background jobs are identified by immutable IDs.

Typical lifecycle:

```
Queued

↓

Running

↓

Completed

↓

Failed

↓

Retried
```

Clients should poll job status or subscribe via future notification mechanisms.

---

# Race Simulation

The backend never simulates races.

The browser owns:

- runner movement;
- timing;
- obstacle progression;
- animations.

The backend only persists results after completion.

This minimises latency and infrastructure cost.

---

# Mathematics

Version 1.0 generates mathematical problems locally in the browser.

The backend stores:

- difficulty settings;
- historical performance;
- progression.

It does not validate every answer.

This enables offline play and reduces server load.

---

# Authentication

Authentication is handled centrally.

The backend trusts only authenticated requests.

Child profiles are scoped to a parent account.

Authorisation decisions occur on the server.

The frontend is never trusted for access control.

---

# Configuration

Configuration is provided through environment variables.

Examples:

- database connection;
- object storage;
- API keys;
- logging level;
- feature flags.

Configuration must never be hardcoded.

---

# Feature Flags

Feature flags are evaluated in the backend.

Examples:

- Story Mode;
- AI Tutor;
- Voice Generation;
- Experimental Stadiums.

Flags should be injectable for testing.

---

# Persistence Strategy

Relational data belongs in PostgreSQL.

Binary assets belong in object storage.

The backend coordinates both.

It should never store binary files inside the relational database.

---

# Caching

Caching is an optimisation.

The application must function correctly without cache.

Candidate cache targets:

- avatar metadata;
- frequently requested statistics;
- configuration;
- generated prompt templates.

Cache invalidation must be deterministic.

---

# Error Handling

Errors are translated once.

```
Domain Exception

↓

Application Error

↓

HTTP Response
```

The Domain must never know HTTP status codes.

---

# Observability

Every request receives a correlation identifier.

Logs, metrics and traces should reference the same identifier.

This enables end-to-end diagnostics.

---

# Logging

Log:

- API requests;
- background jobs;
- retries;
- failures;
- AI provider interactions;
- authentication events.

Avoid logging:

- secrets;
- tokens;
- personal data;
- generated images.

---

# Security

Security requirements include:

- HTTPS only;
- secure cookies where applicable;
- JWT access tokens;
- refresh tokens;
- CSRF protection when required;
- input sanitisation;
- rate limiting;
- request size limits.

All external input is treated as untrusted.

---

# Testing Strategy

Every layer has dedicated tests.

Presentation:

- endpoint behaviour.

Application:

- orchestration.

Domain:

- business rules.

Infrastructure:

- integrations.

The majority of tests should target the Domain layer.

---

# Deployment

Backend instances are stateless.

Any instance should be able to process any request.

Persistent state exists only in external services.

Horizontal scaling should require no code changes.

---

# Non-Goals

Version 1.0 intentionally excludes:

- microservices;
- GraphQL;
- WebSockets as a core dependency;
- distributed messaging platforms;
- event sourcing;
- CQRS;
- server-side gameplay simulation.

These may be reconsidered only if future requirements justify the additional complexity.

---

# Consequences

## Advantages

- Clear separation of responsibilities.
- Excellent testability.
- Low operational complexity.
- Easy horizontal scaling.
- Offline-capable gameplay.
- AI provider independence.
- Fast request handling.
- Maintainable domain model.

## Trade-offs

- More application-layer orchestration.
- Explicit repository interfaces increase boilerplate.
- Background jobs introduce eventual consistency for AI-generated assets.
- Some workflows require polling while asynchronous jobs complete.

These trade-offs are accepted because they maximise maintainability and user experience.

---

# Summary

The backend acts as the orchestration layer of Math Racers.

It owns business workflows, persistence, authentication and AI integration while deliberately excluding gameplay simulation.

This separation keeps races responsive, enables offline functionality, reduces infrastructure costs and preserves a clean boundary between gameplay and server-side services.
